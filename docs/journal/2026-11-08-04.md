### v9s.33 · 脊柱分段、动态平衡量化、卡肉分层

> 上一轮评审里标记「暂缓」的三条建议被判定为可做，另修两条试玩反馈 + 一条发布故障。
> 核心结论先放前面：**脊柱分段不需要改任何动画数据**，因为剪辑描述的是躯干总角。

#### 1. 脊柱分段：改分配点，不改数据

`view.animation.spine = { enabled, waist: 0.58, chest: 0.42, neck: 0.16, chestPivot: 0.42 }`

骨架从「一整段 `upper`」变成「腰 `upper` + 胸 `chest`」两个串联节点，肩与头挂到 `chest`。
所有姿态层（步态、持械、挥击、受击、惯性）**照旧只写 `upper`**，在写完之后调一次
`splitSpine()`：按 `0.58 / 0.42` 归一化权重把三轴拆到两段，颈段只吃俯仰
（`headPivot.rotation.x -= totalPitchX * neck`），扭转仍归 gaze 的 `headYaw`。

为什么数据不用动：`R(w·θ) · R(c·θ) = R((w+c)·θ)` —— 绕同一竖直轴的角度可加，
总角不变则世界朝向不变。用例逐帧比对「分段开 / 关」的躯干总角，误差 < 1e-6。

拆分发生在帧尾，因此**它之后读 `upper.rotation` 的代码拿到的都是腰段局部角**。
本轮实际撞了 5 处，都不报错、只是数值偏：

| 位置 | 症状 | 修法 |
|---|---|---|
| `applySecondaryGrip` 的 `worldToLocal` | 大剑左手离柄 0.389m | 用 `(spineOn ? chest : upper)` |
| 头部世界朝向 | 偏 0.0219 rad | `torsoYaw()` = upper + chest |
| `applyWrist` 的 yaw | 腕部外撇跟着少 42% | 改读 `torsoYaw()` |
| `hurt-rig` 取躯干网格 | `children[0]` 现在是 `chest` 组 | 网格命名 `torsoLower / torsoUpper`，按名取 |
| 4 个测试的断言 | 期望值差 42% | 统一读「总角」= upper + chest |

#### 2. 动态平衡量化：手臂配重是无效解

`solveBalance(points, support, vx, vz)`（纯函数，`src/presentation/balance.ts`）：

- 质心 = 各质点质量加权；捕获点 `XCoM = COM + v · √(h/g) · τ · 4`（站立时退化成 COM）；
- 支撑面 = **双脚**地面投影包围盒（只算着地脚的话，单脚支撑期余量会在 −1 与 +1 间乱跳）；
- `score = 1 − max(|dx|/halfX, |dz|/halfZ)`，0 = 压线、1 = 正中。

按原计划先做了「超界就加大另一侧手臂外展」的闭式解，实测**外展 40° 只把质心拉回 2mm**
（5kg / 70kg × 0.42m），对余量毫无意义，函数直接删掉。改成**骨盆侧移**：
上半身约占体重 60%，横移 1cm 就是 6mm 质心位移，差一个数量级。

| 读数 | 值 | 解读 |
|---|---|---|
| 待机（剑盾） | 0.78 | 正常站姿 |
| 待机（双剑） | 0.76 | 双持略宽 |
| 待机（大剑） | 0.26 | **对**：剑身伸出支撑面外，真人也要靠肌肉代偿 |
| 自动修正 A/B | 侧向偏移 −4.4mm | `maxShift 0.045` / `counterRate 8` |

#### 3. 卡肉分层：让时长自己带出层次

```
stop = hits.hitstop[受击类型] × hits.hitstopByWeapon[武器]
     = { light 45ms, heavy 70ms, knock 100ms } × { 大剑 1.3, 法杖 1.1, 剑盾 1.0, 弓 0.9, 双剑 0.85 }
```

| 组合 | 时长 |
|---|---|
| 大剑 · 击飞 | 130ms |
| 大剑 · 重击 | 91ms |
| 剑盾 · 重击 | 70ms |
| 双剑 · 重击 | 59.5ms |

表现层不另立档位表，**由时长反推**：`tier = clamp(dur/0.1)`、震动 `0.34 + 0.48·tier`、
微推 `0.03 + 0.05·tier`。Core 调时长、表现自动跟上，不会出现「停得久却震得轻」。
微推是位移式的（改 `camera.position` 不改朝向），衰减 `exp(-13t)`，背景不旋转、只有一记顶。

`diagnostics().camera.kick` 是包络值（采晚 0.35s 就读成 0），`kickCount` 才是「有没有发生」的证据
—— 本轮冒烟就因为只读 `kick` 误判过一次。

#### 4. 收势期间的下盘滑行

现象：攻击结束还在按方向键，角色在平移、腿停在攻击跨步姿态、脚被 IK 钉住。
根因不是 IK，是**两条姿态来源抢同一条腿**：攻击跨步一直写到 `settle` 结束。

```
cap  = { windup 0.55, recovery 1.0, settle 1.0 }
ramp = clamp((speed − 0.35) / (1.2 − 0.35))
take = cap × ramp          // 一阶平滑：上升 10 / 下降 6
gaitPose = mixLowerGait(gaitPose, realPose, take)
```

`mixLowerGait` 只插值腿 + 骨盆，保留 `armL/armR/sideLean` —— 上半身还在收招、下半身已经在走路。

A/B 判据换成两条更本质的指标（「脚悬空高度」会被收势姿态本身抬腿干扰）：
**有没有一只脚落地**（`minLift < 0.08`）+ **单脚 z 行程 > 0.1**。

| | 接管开 | 接管关（旧版） |
|---|---|---|
| `legTakeover` | 0.96 | 0 |
| 最低脚离地 | < 0.08（落地） | 0.17（两脚悬空） |
| 单脚 z 行程 | 0.56m | < 0.04m |

#### 6. 线上页面周期性自动刷新

根因不在代码：发布 manifest 的 `runtime.language` 落成 `node`，发布脚本于是按 Node 项目起
`npm start`（= `vite` dev server），HTML 被注入 `/@vite/client`，HMR 一有心跳就整页重载。
改成以 `dist/` 为发布目录后走 `static`（`python3 -m http.server`），已验证线上 HTML 不含 `@vite/client`。

**这类问题本地永远复现不出来** —— 本地一直跑 dev server，刷新是「正常现象」。

### v9s.34 · 渲染插值、三条中风险关闭、clip-lab 提速 33 倍

> 用户问：「慢放时发现动画更新似乎小于渲染帧率，是否需要表现层做平滑处理？」
> 答案：需要，但不是在姿态上抹平 —— 是**在两个模拟步之间插值**。

#### 1. 慢放为什么像幻灯片

Core 固定 60Hz（`fixedDt = 1/60`），`clock.frame()` 每帧只把
`frameSeconds × timeScale` 累加，够一步才 `step()`。于是慢放等价于**降低采样率**：

| 场景 | 模拟 | 渲染 | 观感 |
|---|---|---|---|
| 120Hz、1.0× | 60Hz | 120Hz | 两帧一张画 |
| 60Hz、0.25× | **15Hz** | 60Hz | 每 4 帧动一下 |
| 60Hz、0.05× | 3Hz | 60Hz | 几乎静止 |

修法是标准做法（`src/adapters/pose-interp.ts`）：

```
每个固定步结束：posePrev ← poseCur；poseCur ← capturePose(world)
每帧渲染：      alpha = 累加器剩余 / fixedDt
                render(applyPose(world, blendPose(posePrev, poseCur, alpha)))
```

只插**连续量**（位置 / 朝向角 / 步相 / 攻击进度 / 受击计时），角度走最短弧；
离散量（武器 / 阶段 / 连击段 / 攻击 id / 卡肉开始结束 / 假人模式）进 `discreteKey()`，
一变就整体 snap。

| 指标（60 帧窗口） | 不插值 | 插值 |
|---|---|---|
| 0.25× 慢放下的重复帧 | 35+ | **<3** |
| 120Hz 下的重复帧 | 30+ | **<3** |
| 总位移差 | — | < 一个模拟步（没有造假位移） |
| 单帧最大位移 | — | < 1.35 × 一步（不会跳） |

代价是**半帧延迟**（约 8ms）。`view.renderInterp.enabled` 与
`__harness.setRenderInterp(on)` 可随时 A/B。

另外新增 `view.renderPose()`：**渲染位姿**（不是 Core 状态）。
两者的差就是插值的贡献 —— 验收「画面连不连续」必须读它，
读 `world.character` 会把插值看没了（本轮就被这个坑了一次）。

#### 2. 三条中风险

| 风险 | 处理 | 验证 |
|---|---|---|
| `splitSpine()` 是帧尾隐式改写，之后读 `upper.rotation` 静默偏小 42% | 新增 `torsoTotal()` 作为唯一总角入口；帧尾比对残差写进 `spineDebug().leak` | 用例断言 `leak === 0`；故意把 total 读错会立刻非零 |
| 平衡反馈闭环相位滞后（`counterRate = 8` 按「不抖」调） | `feedForwardLateral(lateral, vLat, 0.12)` 外推 + `counterRateFor(base, load, 1.6)` 负载加权 | 纯函数 3 例 + 骨架 A/B（首帧修正不晚于旧版）；`predLead = 0` 精确回旧行为 |
| `test:affected` 靠正则解析 import，规则不完备 | 换 esbuild `metafile` 真实模块图（`packages: 'external'`，多入口给 `outdir`） | `--graph` 自检：82 个测试文件「正则 vs esbuild」**零差异**（说明换图是去掉手写规则，不是修了漏检） |

前馈的两个刻意边界：**外推会穿过中心时归零**（反号会让骨盆来回抽）；
**双脚离地时归零**（支撑面退化，外推没有意义）。

#### 3. clip-lab：4m30s → 8.2s

先量再改。九段全量 270s 拆开是：**干活 8s，浪费 262s**。

| 环节 | 旧 | 新 |
|---|---|---|
| 采样 | 400+ 次 `page.evaluate`，每帧再跑 4 帧预热 | 1 次 evaluate 跑完整批，预热只在段首 |
| 收工 | `browser.close()` 卡 30s 超时（软件渲染下渲染器不放行） | 按 `--user-agent` 标记 `pkill` + 守护线程 `pw.stop()` |
| 截图 | `check` 默认开（每张约 3s） | 默认关，`--shots` 才出 |

预热从「每帧 4」降到「段首 12 + 其余 2」是拿数据换的：
与逐帧 4 次预热相比，九段最大扫角差 **0.8°**、最大仰角差 **0.86°**，耗时少 23%。

耗时现在直接打印在报告里（扫描 / 启动 / 加载 / 截图 / 总），
`CLIP_LAB_TIMING=1` 额外打印清理与进程退出 —— 下次变慢能一眼看出卡在哪。

#### 4. 顺带修掉的诊断口径

`combo` 的「锚点衔接」原来只报**刃身**跳变，九段里六段 ⚠️/❌（最大 139°），
看着像六处连击断裂。实际是口径问题：段首姿态按 `strike` 曲线淡入（`t=0` 时 ≈0），
剑必然回到接近中位，段末却是满幅 —— 相减天然一百多度。

现在并列报**身体跳变**（上段末 `bodyYaw` vs 下段起 `bodyYaw`）：
大剑 10° / 0°、剑盾 0°、双持 0°，**躯干是连续转过去的，三连击结构没问题**。
阈值也校准到报告自己的说法（>70° 提醒、>130° 才算「会看成闪一下」）。
