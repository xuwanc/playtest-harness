### v9s.35 · 朝向平滑、插值清单补齐、发布自检

> 用户反馈：「慢放时，似乎角色方向也是一顿一顿的，也需要平滑，晚半帧关系不大。」

#### 1. 为什么位置顺了、朝向还顿

v9s.34 的插值让**位置**在两个模拟步之间线性连续，但朝向暴露的是**角速度**：

- 0.25× 时模拟只有 15Hz，插值把「一步转过 6°」摊成 4 段线性小坡；
- 每段交界处速度突跳一次，位置这种一阶量看不出来；
- 但手 / 肩 / 武器挂在 **0.4~0.8m 半径**上，角速度突跳乘上半径就是线速度突跳 → 肉眼读作「一顿一顿」。

另外还有三处**根本没进快照**的连续量在慢放时按 15Hz 跳：`dash.timer`（翻滚整圈）、
`turnInPlace.progress`（原地转身踏步）、`playerLink.progress`（举盾前撞），以及
`velocity`（下盘步态方向 / 摆幅按它分解）。

#### 2. 两条修法，一层治根、一层治手感

**根因层：把表现层真正读到的连续量都纳入插值。** 快照新增 `velocity` /
`dash.timer` / `turn.progress` / `link.progress` / 假人速度；三套状态机的**阶段**
进 `discreteKey` —— 切阶段那一帧 snap（避免把两段姿势抹平），阶段内部连续。

**手感层：渲染根节点朝向低通。** `view.renderInterp.yawSmoothMs`（默认 35ms）：

```ts
// three-scene.render()
yawTarget = c.bodyYaw;                       // 插值后的目标（Core 值，未改）
playerRoot.rotation.y = yawSmoother.update(yawTarget, frameDt, tauMs);
```

- 只改「给眼睛看」的根节点，不回写 Core；判定 / 命中 / 相机目标全读原始 `bodyYaw`。
- 指数趋近 `k = 1 - e^(-dt/tau)`，与帧率无关（60Hz 与 120Hz 收敛曲线一致，实测差 < 1°）。
- 单帧跳变 ≥ 60° 判**瞬移**（传送 / 复位 / 换体型 / 测试工位），直接对齐，不会横着飘。
- `0` = 关闭，A/B 对照用。

#### 3. 量化

| 场景（0.25× 转身 240 帧） | 画面不动帧 | 单帧最大转角 | 终点朝向 |
|---|---|---|---|
| 不插值（v9s.33 行为） | **180 / 240** | 4.6° | 41.7° |
| 仅插值（v9s.34） | **0 / 240** | 1.15° | 44.2° |
| 插值 + 低通（v9s.35） | **0 / 240** | 1.08° | 44.7° |

三组终点差 < 0.1°：**低通只改「怎么到」，不改「到哪」**。
浏览器实测（960×600 软件渲染）：`yawDebug()` 的 `shown` 逐帧变化、与 `target` 峰值差 **2.6°**（≈半帧）。

阶跃响应（单帧 6° 台阶）：低通把它拆成 3 帧，单帧最多吃掉 60%，8 帧内收敛到 0.05° 以内。

#### 4. 顺带把三个待办优化落地

1. **发布自检 `npm run smoke`（8 项，全为画面层事实）** —— 这次踩到的坑正是它的存在理由：
   单测 843 例全绿、`tsc` 无错、`vite build` 成功，但页面可能因为「无头浏览器拿不到 WebGL」
   停在空 `#app`。smoke 检查：harness 就绪 / 无 pageerror / `alpha` 有变化 / 位置跟随
   （滞后 < 0.4m）/ `shown` 持续变化 / 朝向滞后 < 25° / 慢放无「不动帧」。
2. **clip-lab 无头启动摘 `DISPLAY`** —— 沙箱里 `DISPLAY=:0` 会让无头 chromium 走 X11 EGL，
   报 `eglInitialize SwANGLE failed: EGL_NOT_INITIALIZED`，随后 THREE 拿不到上下文。
   以前偶发、这次必现，现象是「页面没准备好（harness: False）」，很容易误判成构建坏了。
3. **插值白名单显式化** —— 哪些量进快照、哪些进离散键，现在每条都在 `pose-interp.ts`
   的注释里写清「表现层哪里读它、不插值会怎样」，新增表现层字段时照抄这个规矩。

#### 验收

  三套状态机切阶段 snap / 整链三层对比 / 阶跃响应。
- `npx tsc --noEmit`、`npx vitest run`（**83 文件 / 843 例**）、`npm run verify:portable`、
  `npm run build` 全通过。
- `npm run smoke` **8/8 PASS**（0.25× 采样 24 帧，朝向滞后峰值 2.6°，零增量帧 0/22）。
- clip-lab 九段 `check` 全 PASS（扫角 / 仰角未变，摘 `DISPLAY` 后无头启动恢复正常）。

### v9s.36 · 卡肉时机对齐（刃身扫掠门）

> 用户反馈：「现在攻击的卡肉，武器还没打到人就卡肉了，手感不好。」

#### 1. 先定性：这不是表现层能修的问题

卡肉的载体是 `CombatState.hitstop`，它**在 Core 里**冻结整条攻击时间轴：

- `advancePhase` 在 `hitstop > 0` 时直接 return（`phaseTimer` 不推进 → 动作定格）；
- `combatUpdate` 把前冲冲量与水平速度一起归零（定格时脚不飘）；
- 它还是插值离散键 `discreteKey` 的一项 —— 冻 / 解冻那一帧必须 snap，不能被插值抹成渐变。

所以「表现层晚半帧再卡」做不到：Core 已经停了，画面再走半帧就等于**逻辑与画面错位**，
解冻时还会把这段错位补跳回来。必须在 Core 里改**判定时机**。

#### 2. 根因：命中窗口从 active 第 0 帧就开判

`playerHits` 的窗口是 `hitWindow.start = 0`，即 active 第一帧就开始扫扇形。而动画的挥击曲线是：

```
swingCurve(progress):  <0.22 蓄势(-1) → 0.22~0.42 挥出(-1→+1) → 0.5 保持 → 收势
```

剑盾第一段 active 起点的 `attackProgress ≈ 0.196` → `swingCurve = -1`，**刃身还在身后最高点**。
但扇形 + reach 已经满足，于是当帧命中、当帧设 `hitstop`，画面就定格在「举着刀没动」的姿势上，
45~70ms 之后才开始真正挥出去 —— 这就是用户看到的「武器还没打到人就卡肉」。

实测（浏览器，站在假人前 0.95m）：

| | 命中时 u | attackProgress | 刃尖相对角 | 刃尖到目标 |
|---|---|---|---|---|
| 修复前 | 0.077 | 0.217 | +160°（身后） | 2.00m |
| 修复后 | 0.590 | 0.362 | −2°（正对） | 0.33m |

#### 3. 修法：给判定加一道「刃身扫掠门」

`WeaponProfile.hitSweep`：

```jsonc
"sword-shield": {
  "hitSweep": {
    "tolDeg": 12,
    "byCombo": {
      "1": { "pts": [[0, 148], [0.2, 125], [0.4, 68], [0.6, -16], [0.8, -78]] },
      "2": { "pts": [[0, -77], [0.2, -68], [0.4, -4], [0.6, 67], [0.8, 120]] },
      "3": { "stabU": 0.42 }     // 突刺：刃尖角几乎不变，用「伸出去到位」代替扫掠
    }
  }
}
```

- `pts` = `[u, 刃尖相对身体朝向的水平角]`，Core 线性插值出 `ang(u)`；
  命中条件是**目标方位角落在 `[ang(0), ang(u)]` 区间（两端各放宽 `tolDeg`）内**。
- `stabU` = 突刺 / 下劈这类角度几乎不变的段：`u < stabU` 一律不判。
- 数据不是手写的：用 `clipLab.preview()` 把 `progress` 逐 5% 摆一遍，读 `bladeWorld()` 的
  刃尖世界坐标反算相对角 —— **与真实剪辑同源**，动画改了重新采一遍即可。

判定流程变成：`扇形（arcDeg） → 距离（reach） → 扫掠区间（本帧刃身扫过）`。
范围与数值**一个都没动**，只改了「什么时候开始算」。

#### 4. 副作用与可调性

| 事项 | 影响 | 怎么调 |
|---|---|---|
| 按键到命中 | +40~70ms（剑盾一段最多，大剑二段几乎没有） | 这是把「提前判」改成「刀到才判」；嫌慢把 `tolDeg` 从 12 调到 24~32（每 +10° 大约提前 0.03u） |
| 命中率 / 伤害 / 击退 / 卡肉时长 | 不变 | 窗口仍是 `hitWindow`，扫掠门只推迟不否决（窗口内一定会扫到） |
| 回滚 | 删掉该武器的 `hitSweep` 即精确回到 v9s.35 行为 | 三段各自独立，可只回滚某一段 |
| 动画改动 | 曲线会漂 | 改完剪辑重跑一遍采样（`tools/clip-lab` 有对应探针），或暂时删配置 |

#### 验收

- 新增 `tests/v9s36-contact.test.ts`（7 例）：命中 u ≥ 0.35 / 扫掠区间覆盖目标方位 /
  删配置回旧行为 / 侧面比正面先吃到刀 / 突刺段 `stabU` 前不判 / 正后方打不到 / 反手段不被拖晚。

- 浏览器实测剑盾三连：3/3 命中，命中 u 分别为 0.59 / 0.46 / 0.46。

### v9s.37 · 卡肉节奏（接触瓦片）、大剑击地、扫掠采样工具

> 用户问：「卡肉时有没有更合适的节奏做法，比如动画减速、扫过后再加速？战神的卡肉节奏是怎么做的？」
> 以及：「动画修改时自动提取扫掠判定数据；大剑第三击落地时增加击地范围攻击。」

#### 1. 战神怎么做的

God of War (2018) 的卡肉有两个容易被忽略的特征：

1. **每一击都卡**，不是只给重击。Santa Monica 的做法是命中瞬间把**攻击者和目标一起 pop 到
   「第一帧接触姿势」**并短暂保持 —— 不是随便冻一帧，而是先把双方钉在「刀贴在肉上」那一刻。
2. **正的重量靠别的通道扛**：镜头震动被**故意调小**（为了多目标可读性），
   冲击感交给重低频音效、大幅挥击弧线、夸张的受击姿势（翻飞 / 空中连击）。

对我们有两条直接推论：

- 「每击都卡」只有在**单次很短**时才成立，否则三连会变成三段慢动作 → 必须做**连段衰减**；
- pop 的姿势必须是真接触帧 → 这正是 v9s.36 的刃身扫掠门在做的事（先有它，瓦片才有意义）。

#### 2. 为什么不是「减速 + 加速」这么简单

纯减速（比如全程 0.3×）读起来是「这一段变慢了」，不是「打实了」—— 它缺一个**陡的入口**。
真正有效的形状是三段：

| 段 | 速率 | 时长 | 读感 |
|---|---|---|---|
| 保持 hold | **5%** | 45 / 70 / 100ms（轻 / 重 / 击飞，× 武器 × 连段） | 黏住，不是卡死 |
| 释放 release | 5% → 100%（ease-out） | 55ms | 「脱开」的那一下 |
| 偿还 payback | **150%** | 直到债务还清 | 后半段略快，把时间还回去 |

第三段是关键：**不还债的话每一击都会把动作拉长 45~130ms**，连击越打越黏。
还债之后总时长守恒，玩家感觉不到「这一刀变长了」，只感觉到「中间顿了一下」。

单测实测（剑盾一段，从起手到 idle）：

| 版本 | 帧数 |
|---|---|
| 完全不卡（基准） | 38 |
| v9s.36 硬冻结 | 41（+3 帧，全落在这一刀上） |
| v9s.37 瓦片 + 偿还 | **38**（把 3 帧还回去了） |

#### 3. 实现：`hits.hitstopWarp`

```jsonc
"hitstopWarp": { "enabled": true, "holdRate": 0.05, "release": 0.055, "payback": 1.5, "paybackBudget": 0.6 },
"hitstopComboFalloff": [1, 0.85, 0.72]
```

- Core 里 `advancePhase` 不再是 `if (hitstop > 0) return;`，而是 `phaseTimer += dt * animRate(...)`。
  保持期只走 5% 的进度 —— 画面仍在极缓慢地动，读作「黏」而不是「死机」。
- 表现层跟着**同一个速率**走：`animDt = frameDt * combat.warp` 传给骨架 / 假人 / 拖尾。
  以前是 `if (!frozen)` 整个跳过；现在两边同速率，不会再出现「Core 慢放、画面静止」的错位。
- 债务逐帧累加（保持段和释放段都在欠），进入偿还时按 `recovery × (payback-1) × 0.6` 封顶，
  超出的作废 —— 否则收招会抽搐。
- `enabled: false` 时 `animRate` 返回 0，与 v9s.36 **逐帧等价**（原 v9s.29 卡肉用例原样通过）。

#### 4. 大剑第三击：击地范围攻击

刀身扫掠是「正面一条线」，砸地是「圆心一圈」。数据：

```jsonc
"groundSlam": { "slamU": 0.6, "radius": 2.4, "knockback": 0.9, "type": "knock", "onlyUnhit": true, "holdMul": 1.7 }
```

- `slamU = 0.6` 不是拍的：采样得到刃尖高度在 **u ≈ 0.605 穿过 y=0**（`--heights` 模式直接打印）。
- 判定顺序：**先刀身、后击地**。同一帧正面目标按刀结算并进 `hitIds`，击地只补「刀没碰到的人」
  （`onlyUnhit` 默认 true）—— 扩大覆盖，不叠伤害。想叠伤害把它设 false。
- 表现：贴地尘环（两圈错开扩散，半径 = 真实判定半径，玩家能「看着圈躲」）+ 比普通命中更重的镜头下压。
  触发读的是 Core 的持久字段 `slamAttackId`，不是事件队列 —— 低帧率一帧多步时事件会只剩最后一帧的。
- 实测（3 个假人：正前 1.0m / 侧前 1.5m / 身后 1.6m）：一刀 3 个全中，`slamAttackId` 从 0 → 1，
  卡肉 0.13s（正面）+ 0.22s（击地，×1.7）。

#### 5. `npm run sweep`：扫掠数据自动采样

```bash
npm run sweep -- --check                    # 采样 + 对比，不改文件
npm run sweep -- --write                    # 写回 config/game.json
npm run sweep -- --heights --weapon greatsword --combo 3   # 找砸地时刻
```

三个必须做对的地方（踩过才知道）：

1. **减掉根节点实际朝向**。`bladeWorld()` 是世界坐标，而角色在主循环里一直在被索敌转过去；
   不减 `yawDebug().shown` 的话，曲线会随「采样那一刻角色恰好转到哪」漂几十度。
2. **每个采样点要预热够**（默认 16 帧）。`preview` 只改表现入参、跑真实 `render()`，
   腕部滞后 / 副手握持是**有惯性**的，跳进度后不预热读到的是过渡帧。
3. **u 是 active 内进度**，转 `attackProgress` 要按 `(windup + u×active)/total` —— 直接拿 u 当 progress 会整段偏。
