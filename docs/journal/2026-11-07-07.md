### v9s.24 · 「武器像焊在手上」：腕关节、滑握、可松手

> 反馈：「看到了修改，有一个问题，武器现在像焊在手上了。1. 应该给双手都加挂点来驱动
> 动画武器相对手的动画？2. 是否应该将动画数据抽出一个格式？3. 按目前的情况是否需要
> 对应做一个方便你做动画的小工具？」

#### 诊断：不是幅度不够，是链路少了一节

「焊死」是结构问题。翻一遍链路，五处叠加：

| 位置 | 旧状态 | 后果 |
|---|---|---|
| `mountR` | `rotation.set(rp, 0, rz)`，`ry` 恒 0，`rz` 是 `greatswordYawDeg × d` 常量 | 剑相对手只有俯仰，且是整段线性插值 |
| 攻击时 | 只有 `mountR.rotation.x` 被 `swingMountPitch` 覆盖 | 没有惯性、滞后、过冲 |
| 腕关节 | 不存在，`armR.hand.add(mountR)` | 肩→肘→手，挥剑最后 30ms 的加速段丢了 |
| `mountL` | 存在，但大剑时只挂了个 `0.12×0.2×0.12` 方块占位 | 真握持是左臂 IK 追 `mountR` 上的点，左手从不驱动武器 |
| 握持权重 | 无，只有 `attackBlend` 淡入 | 不能松手，够不到只能拉长胳膊 |

所以「给双手都加挂点」这个直觉是对的，但**不是加两个父节点**：两个挂点本来就有，
缺的是自由度、驱动、和副手的约束权重。

#### 做法一：hand 与 mount 之间插 wrist

```
hand → wrist(3DOF) → mount → weapon
```

`wrist` 默认 identity，不写它就是旧版逐帧一致（调试面板可整体关掉做 A/B）。

驱动来自两个已经写好的量，只做差分，不引入新时间源：

```ts
const pitchVel = (armR.root.rotation.x - prevArmPitch) / dt;   // 臂部俯仰角速度
const yawVel   = wrapAngle(upper.rotation.y - prevTorsoYaw) / dt; // 躯干扭转角速度

const gate = 0.15 + 0.85 * attackBlend;   // 见下
wantPitch = -pitchVel * lag * gate + dragRun;
wantTwist =  yawVel  * twistLag * gate;
// 一阶平滑（不是弹簧：二阶系统对可变 dt 不稳，暂停单步 / 时间缩放会漂）
wristPitch += (wantPitch - wristPitch) * (1 - Math.exp(-rate * dt));
```

三个符号 / 系数上的判断：

**① 为什么用一阶平滑而不是弹簧。** 二阶弹簧只有固定步长才稳，而这个项目的 `dt` 会被
暂停单步、时间缩放、掉帧改来改去。一阶指数平滑对任意 `dt` 都收敛，而且「腕部因为阻尼
大而跟手慢」本身就是一阶低通的物理直觉。

**② 为什么按攻击权重缩放。** 人拿重物走路时手腕是**主动锁定**的（握力 + 前臂肌群）。
不缩放的话，走路摆臂 6.9 rad/s 会解出 15° 的滞后，实测读起来像手腕脱臼。留 0.15 的底，
让跑步时剑仍有一点跟随感。

**③ 换段那一帧必须丢掉差分。** `attackProgress` 从 1 跳回 0，手臂角度是**瞬变**的，
拿它差分会得到几十 rad/s 的假角速度，腕部「啪」地甩一下（实测单帧 10°）。
按 `comboIndex` 变化判定，直接重新对齐基准。

**跑动拖拽单独一路**，不参与 `gate` —— 它要治的正是「非攻击状态下剑焊死」：

```ts
dragRun = -clamp(speedRatio, 0, 1.4) * runDrag;   // runDrag = 0.11 rad ≈ 6.3°
```

#### 做法二：握点沿柄滑动 + 够不到就虚握

旧版握点是「帧内一次性迭代到目标值（每步 ×0.45，最多 5 步）」，于是手臂姿态一动，
握点就在两帧之间从柄尾瞬移到护手。现在拆成两步：

```ts
// 1) 求「需要滑到哪」：每步 ×0.78，最多 18 步（细步长）
for (k = 0; k < 18 && probe.dist > maxReach; k++) { gy *= 0.78; probe = probeAt(gy); }

// 2) 握点是实体：一阶跟随，不再瞬移
gripSlide += (gy - gripSlide) * (1 - Math.exp(-slideRate * dt));
```

**不做「追不上就直接跳到位」的兜底**：平滑值滞后于目标时手确实会短暂够不到，但那正是
虚握 —— `solveTwoBoneIK` 会把手臂解成伸直指向柄，手停在臂展末端。兜底反而会在手臂
到达最高点的那一帧把握点从柄中段瞬移到柄顶，比虚握难看得多。

握持权重随臂展比衰减，这是本轮唯一「允许看起来没握死」的地方：

```ts
soft  = smoothstep(gripStart, maxStretch, reach);   // 1.02 → 1.30
gripW = 1 - soft * (1 - twoHandMinGrip);            // 默认松到 0.62
blendIKAngles(..., weight * gripW, ...)
```

为什么不是干脆不拉长：实测举顶时左肩到柄上副握点 0.72m，而单臂只有 0.42m ——
差 1.7 倍。`twoHandMaxStretch` 只到 1.3，剩下的缺口只能靠「手松一点」填。
0.62 是踩出来的：0.5 时左手离柄轴 0.20m（v9s.23 的贴柄断言直接挂掉），
0.62 时压回 0.19m 以内，同时胳膊不再明显变细。

#### 没做的两件事（以及为什么）

**PoseClip 格式没做。** 判断是该做，但不该现在做，也不该做成 glTF：骨骼是程序生成的
体素、没有蒙皮权重，glTF 的通道名绑定全部对不上；而现在的动画强在响应式（步态跟速度、
受击跟力度、IK 跟地形），这些烘焙不进 clip。真要抽，抽的是「稀疏关键帧 + partial pose」，
融合靠已有的层级：`L0 base(gait/lean/hurt) → L1 clip 采样 × weight(override) → L2 左手IK/滑握`。
现在的 `swing-pose.ts` 已经是「2 帧 + 线性插值」，泛化成「N 帧 + 时间轴 + 通道集合」就是
PoseClip —— 格式不是从零引入，是把跑通的那一半抽出来。这一步等有第二个技能需要复用动作时再做。

**K 帧工具没做。** 值得，但第一版不该是时间轴编辑器（2~3 周，而且体素方块人上大概率
用不到曲线编辑）。该做的是「摆姿势 → 记一帧 → 挪时间」的 K 帧环，项目已经有 80% 的基础
设施（`__harness` 单步、读全关节、热改 config、截图），缺的只是记录 / 导出 / 播放。
判断点不是工具值不值，是**打算做多少个技能**：3~5 个近战 + 2~3 个远程，K 帧环足够。
