# 2026-11-09-05 · 协同推送：改动上功能分支（读用 git / 写走 MCP 网关）

## 触发

用户问：「如果协同工作的话 是不是把你的修改推到分支上？如果是的话，先推送一波」。
**回答：是**，但推的是**独立功能分支**，不是 `main`——别人才能 `fetch` / review /
开 PR，多 agent 并行不互相覆盖，主线不受影响。用户明确通知后执行推送。

## 实测：通道到底是什么（推翻旧文档）

| 尝试 | 结果 |
|---|---|
| `git ls-remote origin` | ✅ 通，`main` = `5a320f4`，无新推送、无需 rebase |
| `git push -u origin HEAD:refs/heads/feat/...` | ❌ `could not read Username for 'https://github.com'`（**写无凭证**） |
| `git-credential-helper` `credential fill` | ❌ 不产出凭证（只覆盖匿名读） |
| `gh auth status` / `GITHUB_TOKEN` / `~/.config/.../gh-token` | ❌ 未登录 / 均未设置 |
| `tools/gh-commit.mjs`（REST 网关） | ❌ 需自备 token，且只提交「工作区未提交的差异」，推不了本地已有的 4 个 commit 链；默认还写 `main` |
| MCP `push_files` 直接当工具参数 | ❌ 835KB 构建产物无法作为文本参数搬运 |
| **GitHub MCP 网关（脚本直连）** | ✅ 已授权，内容从磁盘读、不受上下文限制 |

结论：`github.com:443` **读**通、**写**不通。旧文档「标准 git push 已恢复」是错的，
本次一并修正。`/root/.codebuddy/.mcp.json` 的 `github` connector 指向
`http://github.agent-gateway.auth-proxy.local/mcp`（REST 路径不透传，只有 MCP 端点）。

## 做法

1. 用 Python 脚本直连 MCP 会话（`initialize` → `notifications/initialized` → `tools/call`）；
   文件内容由脚本 `open().read()` 从本地磁盘读，**不经过对话上下文**，
   因此 1.55MB / 57 文件（含 835KB `dist/assets/main-B6nSWqvr.js`）一次写入成功（12s）。
2. `create_branch` 基于 `main` 建 `feat/integration-grass-wind`（**绝不动 main**）。
3. `push_files` 一次写全部 A/M（31 新增 + 26 修改），
   `delete_file` 清理相对 `main` 已删除的 2 个旧 hash 产物。
4. **树一致校验**：`git fetch` 远端分支 → `HEAD^{tree}` 与 `origin/...^{tree}`
   均为 `4843ea5b6f77847fabfd61fcafe1fc6e06adf5f7`，263 文件，`git diff` 为空。
5. 本地分层 commit（4 个）留备份分支 `backup/local-v9s43-v9s44` @ `f8281ae`，
   再 `git reset --hard origin/feat/...` 对齐 + `set-upstream-to`，避免假分叉。

> 远端 commit 由 API 重建，SHA 与本地不同（远端 3 个 commit：`77ebc89` 主改动 +
> 2 个清理），但 **tree 逐字节相同**。主 commit message 里列出 4 个本地原始 SHA 供追溯。
