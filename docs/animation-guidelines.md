# 动作迭代规范

这份文档回答一个问题：**新加一段连击时，怎么判断它「对不对」**。

它针对的是本项目这套「语义关键帧」（`PoseClip`）的工作方式，不是通用动画教程。
每条都标了对应的代码位置和实测数字，方便直接改数据验证。

---

## 一、连击骨架：锚点与窗口

### 1.1 「对齐同一个 pose」只对了一半

你提的「每击开始结束对齐起始 pose」方向是对的，但**单一 pose 会把三连击变成同一次攻击打三遍**。
实战里用的是**锚点集合**：

| 锚点 | 用途 | 典型姿态 |
|---|---|---|
| `guard` | 默认待机 / 收招归位 | 剑在右前下方，重心居中 |
| `left-finish` | 段 1 收势、段 2 起手 | 剑在左后，右肩前送 |
| `right-finish` | 段 2 收势、段 3 起手 | 剑在右后，左肩前送 |

相邻段**共享**一个锚点就够了，不需要全段对齐。段 1 收在 `left-finish`，段 2 就从
`left-finish` 起手；段 2 收在 `right-finish`，段 3 从 `right-finish` 起手。

> **对齐的不只是手**。手对上了、骨盆没对上，换段时脚会滑一步。锚点至少要锁
> `bodyYaw`、`pelvisX/Z`、`rootYaw` 三项。

**本项目的现状**：走的是「连续承接」而不是「共享锚点」——段 2 的起手是段 1
收势的延长线，段与段之间**故意**不收敛到同一个点。这带来一个必须知道的副作用：

> 段首的幅度由 `attackBlend` 淡入，本来就接近中位；段末是满幅。两者天然差
> **100~170°**（`npm run clip:lab:combo` 实测：大剑 162°/169°、双持 136°/30°）。
> 这个差只能靠 `segBlend`（默认 0.08s）掩过去。

**两条路线，不要混用：**

- **共享锚点**：换段零跳变，但动作幅度受约束，适合轻武器 / 快速连段。
- **连续承接**：动作舒展，但换段必然有跳变，必须把 `cancelWindow` 放在
  「下一段起手方向」上，且 `segBlend` 不能太短。

### 1.2 连击窗口不在「下一招 pose」

你写的是「攻击进行到下一招的 pose 时放缓，给连击窗口」。**时序反了**。

下一招 pose 还没发生，谈不上在那时开窗口。真实的窗口在**挥击到位之后、收势走完之前**：

```
起手 ──── 前摇 ────► 挥出 ──► 命中 ──► 保持 ──► 收势 ──► guard
                          ▲              │
                          └── 窗口从这附近开 ──┘（cancelWindow）
```

- **窗口内按下一击** → 直接切段，跳过剩余收势。这是「连打跟手」的来源。
- **窗口过期** → 老老实实跑完收势回 `guard`。

**本项目**：`core.combat.cancelWindow = 0.45`（按攻击进度归一）。

v9s.28 修了一个真问题：旧的挥出曲线在 `progress = 0.50` 才走满，而窗口
`0.45` 就开了 —— 玩家连打时**剑才走到 64% 就被切走**，衔接处实测跳 85~117°。
现在挥出提前到 `0.42`，窗口打开时动作已经到位。

> **自检**：`cancelWindow` 必须 ≥ 挥出完成点。否则最"爽"的连打方式恰好是最难看的那条路径。

### 1.3 「放缓」只应该发生在命中之后

不要全程减速。正确的三处变速：

1. **前摇**：慢，且可以带一点反向预备。
2. **挥出**：最快，且**持续加速**到命中（ease-in），不能匀速。
3. **命中后**：保持满幅 3~8% 的时间（hit stop / follow-through hold），再回落。

本项目的 `swingCurve`（`src/presentation/voxel-rig.ts`）就是这条曲线：

```ts
if (t < 0.22) return -1;                        // 前摇：停在起手
if (t < 0.42) return -1 + ((t - 0.22) / 0.2) * 2; // 挥出：20% 走完 -1 → +1
if (t < 0.5)  return 1;                          // 保持：8%
return Math.max(0, 1 - (t - 0.5) / 0.5);         // 收势：50%
```

## 二、动态平衡

### 2.1 副手反向是对的，但有三个补充

你提的「挥左手时右手往右后方收」正确。补充：

**① 反向配重有上限。** 双手同柄武器（大剑）做不了反向——副手被 IK 锁在柄上。
只有单手 / 双持才适用。

**② 反向的意思是「副手往自己那侧后方」，不是「往主手的反方向」。**
右手挥出时，左手往**左后**收（不是往右）。这样两把剑是展开的，不是交叉的。
本项目双持中段实测主副手分离 **49.8°**（段 1）；低于 45° 时两把剑视觉上会重合。

**③ 反向的不只是手。** 完整的配重链是：

| 部位 | 动作 | 通道 |
|---|---|---|
| 骨盆 | 向挥击反方向平移 3~7cm | `pelvisX` |
| 躯干 | 侧倾（roll）与挥击方向相反 | `bodyRoll` |
| 肩膀 | 主手侧前送、副手侧后拉 | `shoulderPush` / `shoulderIn` |
| 头 | **不跟着甩**，保持朝目标 | —（当前不做头部独立控制，靠躯干幅度控制） |

### 2.2 舒展 ≠ 幅度大

「动作要舒展」的判据是**关节行程**，不是剑尖扫过多大的角。

- 挥击结束时肘应该接近伸直（本项目 `elbow` 从 `-0.5` 收到 `-0.12`）；
- 起手时肘应是屈的（`-0.5` 左右），才有「蓄力」的形；
- 全程肘角不变 = 抡胳膊，看着像假肢。

双持第三击「展开旋身」是本轮最典型的例子：`armYaw` 从 1.7 展开到 2.1、
`elbow` 收到 `-0.05`（几乎伸直）、两把剑 pitch 保持 3~12°（水平），
刃身分离 **169°** —— 这才叫舒展。不是把剑举高。

## 三、节奏

### 3.1 慢快慢的量化

你说「慢快慢或快快慢」是对的，但需要落到数字上才可执行：

| 阶段 | 建议占比 | 说明 |
|---|---|---|
| 前摇 windup | 18~38% | 最短不能少于 15%，否则看不出预备 |
| 挥击 active | 15~32% | **必须最短**，这一段是爆发 |
| 收势 recovery | 40~60% | 短于 40% 会「刹不住」，长于 70% 拖沓 |

本轮实测（`npm run clip:lab:combo`）：

| 武器 | 前摇 | 挥击 | 收势 |
|---|---|---|---|
| 大剑 | 23% | 26% | 51% |
| 双持 | 20% | 29% | 51% |
| 剑盾 | 20% | 28% | 52% |

**问题**：三种武器、三段的配比**完全一样**。读起来就是「同一个动作点三下」。
下一步应该做成逐段递减：第 1 击 25/25/50、第 2 击 18/25/57、第 3 击 35/20/45。

### 3.2 帧数下限

挥击段在 60fps 下**不能少于 5 帧**（83ms）。少于此刀光来不及成形，
表现层会看起来像「闪了一下就结束」。

按本项目双持最短的 `active = 0.10s` 算，正好 6 帧——这是下限，不要再短。

### 3.3 三连要有起伏

同一套动作连打三次，节奏必须变化，否则玩家感受不到「连段」：

- 第 1 击：建立节奏，中速。
- 第 2 击：更快（承接第 1 击的动量），前摇可以砍到 60%。
- 第 3 击：重，前摇明显变长，收势也长——它是「终结技」。

## 四、容易踩的坑（都是本项目真踩过的）

### 4.1 别让语义漂移

`bladePitch` 是**剑身相对水平面的世界仰角**，不是「相对前臂的角度」。
v9s.25 之前写成了后者，结果手臂一抬高，剑尖就朝天——前两击看起来像举着剑走路。

> 一条通道的语义一旦定死，改它就要重调所有数据。宁可新加通道，不要偷偷改含义。

### 4.2 语义通道不等于骨骼旋转

`armYaw` 曾经是个**假通道**：`shoulder.rotation.order = 'ZYX'` 让它变成了
「绕手臂长轴自转」，实测 −1.4 → 0 只让刃身水平朝向变 25°。v9s.28 把顺序改成
`'YXZ'` 才真正变成肩的水平内摆。

> 加通道时先确认它**真的**能驱动目标自由度，用工具扫一遍量程。量程不够就改骨架，别硬调数据。

### 4.3 截图会骗人

斜俯视相机下，**水平指向远方的剑在画面上是「向上」的**。
v9s.26 因此误判了一次「剑举起来了」。

判断横扫必须读刃身两端的世界坐标：

```js
__harness.bladesWorld()   // { right: {base, tip}, left: {...} }
// 两端 y 差 < 0.03m 才是水平
```

### 4.4 稳态 ≠ 手感

`clip-lab` 的 `preview` 会把姿态定格后渲染 45 帧让腕部滞后收敛，
量出来的是**稳态角度**。真实连打时腕部一直在追，角度会有 ±10~20° 的滞后。

> 角度用工具量，手感必须实时连打看。两者不能互相替代。

### 4.5 命中帧要和视觉最快点对齐

判定结算的时刻（`active` 段）必须落在剑挥得最快的那一帧附近。
v9s.23 之前 `active` 结束时挥击曲线才走到 0.16——判定已经结算、剑还在半路，
观感是「挥了个寂寞」。

> 改 `windup/active/recovery` 之后，一定要用 `clip-lab` 重新确认 `active` 时间段内刃身已经扫过。

## 五、加一段新动作的检查清单

```bash
# 1. 扫角度：仰角是否水平、扫角够不够、有没有朝天
npm run clip:lab -- scan --weapon greatsword --seg 1 --steps 40 --shots

# 2. 连击结构：衔接跳变 / 节奏配比 / 主副手平衡
npm run clip:lab -- combo

# 3. 全段门禁：九段一起跑，不达标直接非零退出
npm run clip:lab:check
```

提交前确认：

- [ ] 横扫段刃身 `|pitch| < 15°`（是平扫，不是举着剑转身）
- [ ] 扫角：大剑 ≥150°、双持 ≥150°、剑盾 ≥120°、盾顶 ≤70°
- [ ] 双持主副手分离 ≥45°
- [ ] `cancelWindow` ≥ 挥出完成点
- [ ] 三段的节奏配比**不完全相同**
- [ ] 副手有反向位移（`pelvisX` 与主手方向相反），不是全身刚性平移
- [ ] 换段没有单帧跳变（`combo` 报告的衔接数 ≤130°）

## 六、留给下一轮的已知问题

1. **三连节奏同质**：三种武器九段配比完全一致，需要逐段差异化（见 3.1）。
2. **段首末跳变大**：连续承接路线的固有代价，若要压到 70° 以内，需要把段首姿态
   往「上一段收势方向」重写，或改用共享锚点路线。
3. **举顶仰角受挂点链限制**：`gs.overhead` 数据写 `bladePitch = 1.62`（93°），
   实测只有 41°。反解链在手臂过顶 + 有 roll 时会饱和。要修得把 `mount.rotation`
   从欧拉角反解换成用父节点世界四元数求解（成本较高，暂记）。
4. **头部没有独立控制**：视线始终跟着躯干走，连续转体时会「甩头」。

## 七、v9s.29 补充：刃口朝向、起手融合、卡肉

### 7.1 「刀身侧面在扫」是几何，不是幅度

刀身模型「薄在 X、宽在 Z」，挂点把刀身放平后，宽面法线正好指向挥击方向 ——
横扫就是拿侧面拍。判据不能看「仰角 / 扫角」，要看**刃尖速度与宽面法线的点积**：

```js
__harness.bladesWorld().right.normal   // 宽面法线（世界）
// 命中帧：|dot(normal, 刃尖速度)| 越小越像「切」，> 0.8 就是在拍
```

滚转必须写在「挂点 → 武器」之间单独一层（`grip`），不能写在挂点上：
挂点的 Y 轴是小臂方向，手臂前平举时它不朝上，写 `rotation.y` 会变成绕小臂转，
刀尖在锥面上打转（实测横扫段仰角多塌 4°）。

### 7.2 刀和小臂要有夹角

刀身仰角是世界语义（0 = 水平），挥击时手臂也几乎水平 → 共线。给挂点一个常量外撇
（`view.weaponMount.swordCantDeg`，单手剑 10°）即可；大剑保持 0，双手握持的臂展已经
没有余量（外撇会把副手握持距离从 0.19 推到 0.23m）。

### 7.3 起手 / 收招必须交叉淡入淡出

只把剪辑首末帧写对是不够的 —— 待机姿态由步态算，剪辑管不到它。做法是每帧在写战斗
姿态**之前**快照骨架，写完按权重混回去（`poseIn 0.1s / poseOut 0.16s`）。
两条容易踩的坑：

1. 收招淡出期间**不能清**战斗姿态状态（要等权重归零），否则淡出没有「来源」；
2. 腿不参与这层混合（腿由 `attackBlend` 管，要跟跨步相位对齐）。

### 7.4 卡肉参数

| 档位 | 时长 | 场景 |
|---|---|---|
| light | 45ms（≈3 帧） | 单手剑 / 双持前两段 |
| heavy | 70ms（≈4 帧） | 三段收招 |
| knock | 100ms（≈6 帧） | 大剑 / 击飞 |

超过 150ms 会把连击节奏拖断；低于 30ms 读不出来（和掉帧分不清）。

**卡肉必须在 Core**：表现层冻结只能停画面，Core 的位移 / 计时还在走，冻结结束会补滑。
实现见 `combat.hitstop`，注意三处：前冲 impulse 与水平速度清零、派生招计时同步暂停、
计时扣减放在帧末（否则少冻一帧、进度偷走 3.6%）。

## 八、v9s.30：把「仰角上限」和「整圈角」两件事说清楚

### 8.1 挂点带上静态 yaw，仰角的物理上限就变成了 90° − |yaw|

欧拉 XYZ 序下 `rz` 先作用，刀身长轴被从 +Y 偏出去：

```
仰角 = asin(cos(z) · cos(θ + chain))
```

`cos(z)` 就是天花板。z = 16° 时最高只能到 74°，数据写 92.8° 也到不了。
所以「举顶不够高」的正解不是换四元数，而是**让外张跟着仰角收缩**：

```
zEff = sign(z) · min(|z|, 90° − |e|)
```

横扫 e≈0 时外张用满（与旧版逐帧一致），越接近竖直收得越小，举顶时归零。

> 用四元数整体替换挂点求解试过：会把手臂的 roll 一起抹平，大剑副手当场脱到 0.37m。
> **改姿态通道时先问「这个量是相对手、还是相对世界」**，能少走很多弯路。

### 8.2 整圈角必须走最短弧

`spinYaw` 推到 2π 后，任何「线性插值回 0」的环节（姿态淡出、换段混合）都会经过 π，
画面上就是倒着转回去一圈。规则：

- 整圈量（`rootYaw + spinYaw`）只做**赋值**或**最短弧插值**
- 需要跨帧累积时先 `wrapAngle`，不要让 2π 与 0 同时进入插值

### 8.3 刀光按「点密度」而不是「时长」配

`maxSamples 8 / life 0.09` 在 60fps 下等于每 4 帧一个点 —— 转一圈就是八边形。
30 点 / 1.5cm 最小步长后弧线才连续。经验值：

| 动作类型 | 一圈（360°）需要的采样点 |
|---|---|
| 快速横扫（<0.2s 扫 180°） | ≥ 16 |
| 原地转圈（0.33s 一圈） | ≥ 24 |
| 慢速蓄力挥 | ≥ 10 |

9. **转身步法变体** —— `turnInPlace` 只有一种节奏。缺「交叉步 / 撤步」，
   长腿体型原地转身仍偏滑。
10. **曲线可视化** —— clip-lab 只有表格。加一张「仰角 / 扫角 / 角速度随 t」的折线图，
    调参时不用在脑子里做积分。


## 十、v9s.31 落地记录：事件扫描与混合时长

### 10.1 关键帧事件的区间语义

三个阶段拼成一个连续标量，**不要**分别对每个阶段做「是否刚进入」判断 ——
单帧跨阶段（低帧率 / 时间缩放）时中间阶段会被整个跳过。

```
scalar(windup, u) = u          // 0..1
scalar(active, u) = 1 + u      // 1..2
scalar(recovery,u) = 2 + u     // 2..3
扫描区间 = (cursor, after]，cursor 初始 -1
```

三个容易写错的边界：

1. **左开右闭**。写成左闭会让同一条通知在相邻两帧各发一次（游标停在刻度上）。
2. **`cursor = -1` 而不是 0**。否则 `u: 0` 的通知永远发不出来 —— 起手第一帧正好在 0。
3. **settle 按 3 结算**。settle 不属于三段，但进入 settle 的那一帧必须把 recovery 末尾
   的 `u: 1` 补发，否则「收招」类事件永远不出现。

卡肉冻结时 `advancePhase` 不推进、也不扫 —— 游标原地不动，恢复后不会补发一串。

### 10.2 命中窗口与去重

`hitWindow` 是 active 段内的 0..1 区间，每帧扫。**必须**配 `CombatState.hitIds`：
窗口内通常有 5~8 帧，没有去重一击会掉 5~8 次血。`hitIds` 每次 `beginAttack` 清空，
所以「同一目标每次攻击只结算一次」是段级语义，不是攻击级。

窗口的 `end` 别写 1：收招前半段刀已经抽回，仍在判定会读成「隔空砍」。
当前配置 0.8~0.9。

### 10.3 混合时长为什么不按角速度线性算

姿态距离的量纲是「十二个通道加权求和」，不同武器落在 1~9 rad，而期望时长是 0.03~0.15s。
直接 `distance / rate` 会大量撞上下限 —— 大部分段要么恒为下限（等于硬切），要么恒为上限
（等于没过过渡）。

所以做两步映射：

```
k    = clamp(distance / segBlendRef, 0, 1)     // segBlendRef ≈ 一次完整换段的量级
span = segBlendMin + (budget - segBlendMin) * k
budget = 本段总时长 × 0.22
```

上限用「本段时长比例」而不是固定秒数，是因为双剑整段只有 0.35s —— 固定 0.14s 上限
在快攻里就是「过渡吃掉四成动作」。`SwingClipRef.blend` 仍可逐段覆写。

### 10.4 还剩下的

第九节第 3~10 条未动。下一批优先级仍是「脊柱分段」，因为它同时改善两件事：
大幅挥击的扭转分布（现在全堆在腰上，瘦高体型像一根棍在转）与受击的部位分层。

## 十一、v9s.32 落地记录：持械姿态与「反馈通道分工」

### 11.1 为什么待机 / 移动姿态要按武器分

同一套程序化摆臂 + 同一个 `mountBasePitch`，换的只是手里的模型。结果是：

- 剑盾的盾牌垂在腿边，看起来像「拎着一块板」；
- 大剑待机双臂自然下垂，剑尖却按 58° 仰角翘着，和「很重」的设定相反；
- 双刀 / 法杖 / 弓站姿没有区别，玩家只能靠武器颜色辨认。

`stance` 只做四件事，且全部是**相对步态基准的偏移**：

```
armR/armL: { pitch, yaw, roll, elbow }  // 肩三轴 + 肘
armSwing                                 // 摆臂倍率（重武器 < 1）
torsoYaw / torsoPitch                    // 躯干朝向
bladePitchDeg / bladePitchOffDeg         // 刀身世界仰角（仅非攻击帧）
```

三步应用顺序很关键：

1. **步态层之后**写手臂：`arm = gait.arm × armSwing + offset`，走路仍有摆动；
2. **`blendCombatPose` 之后**写躯干：`upperYaw += torsoYaw × (1 − combatPoseW)`，
   攻击权重越高越让位；
3. **`applyBladeTarget` 内**只在 `swingBladePitch == null` 时叠加刀身仰角，
   攻击帧完全由剪辑说了算。

不要给 stance 单独做一条「待机 ↔ 持械」时间轴：换武器时 `stanceWeight` 0→1 已经够，
攻击进出继续复用 `poseIn / poseOut`，否则会出现两套淡入淡出互相打断。

### 11.2 反馈通道分工：震动只属于命中

上一版把 `blade-air` 通知接成镜头震动，导致空挥和命中反馈一样。现在定成硬规则：

| 通道 | 触发 | 语义 |
|---|---|---|
| 镜头震动 | 仅 `combat.hitstop > 0` 的上升沿 | 「打实了」 |
| 刀光脉冲 | `blade-air` | 「挥出去了」 |
| 骨架定格 | `combat.hitstop > 0` | 「停住了」 |
| 脚步事件 | `foot-step` | 暂未接表现，留给音效 / 尘土 |

这条规则的价值不是省一次震动，而是让玩家能从反馈**反推判定**：震了就是中了，
没震就是空了。任何「挥击就有」的效果都不该占用震动通道。

`WeaponTrail.pulse()` 的衰减必须帧率无关（指数），否则 30fps 下会拖出一条长亮尾巴。
上限 1.5 是防连击叠加把整块屏幕刷白。

### 11.3 已知边界

- 腿仍是共享步态：剑盾侧身站没有对应的脚位，跳起时回到统一空中姿态；
- `stance` 的躯干偏移与 `chestYaw`（胸随下盘）是两条来源，读数时要相加，
  `gaitDebug().chestYaw` 不会包含持械扭转；
- 大剑待机双臂前收会让肩点前送约 2mm，属于持械基准，不是攻击残留。

## 十二、v9s.33 落地记录：脊柱分段 / 平衡量化 / 卡肉分层

### 12.1 脊柱分段为什么一行动画数据都不用改

先说结论：**现有动画数据可以直接用到有腰 / 胸 / 颈的骨架上**，因为剪辑里写的是
「躯干总角」，不是「腰骨该转多少」。数据侧的三轴（`torsoTwist / torsoPitch / torsoLean`）
是**语义通道**，它们描述的是「整个上身相对骨盆转了多少」，落点在哪根骨上是表现层的自由。

所以实现是「改分配点」而不是「改数据」：

```ts
// 所有姿态层照旧只写 upper（= 躯干总角）
upper.rotation.x = ...;   // 数据来的总角
// 最后一刻拆成两段：腰吃 0.58、胸吃 0.42（权重自动归一化）
splitSpine();
```

绕同一根竖直轴的旋转是可加的，`R(w·θ) · R(c·θ) = R((w+c)·θ)`，所以
**世界朝向完全不变**——这也是「数据不用改」的数学依据，用例里逐帧比对
「分段开 / 关」的躯干总角，误差 < 1e-6。

几处容易踩的坑，都是这轮实际踩到的：

| 坑 | 现象 | 处理 |
|---|---|---|
| 肩挂到 `chest` 后副手 IK 用错父节点 | 大剑左手离柄 0.389m | `(spineOn ? chest : upper).worldToLocal()` |
| 头挂到 `chest` 后补偿少算一段 | 头部世界朝向偏 0.0219 rad | `torsoYaw()` 改成 `upper + chest` |
| 测试读 `upper.rotation.x` | 只剩 40% 的量，断言全崩 | 测试统一读「总角」= upper + chest |
| 躯干网格变成两个 | 按 `children[0]` 取网格拿到的是 `chest` 组 | 给网格命名 `torsoLower / torsoUpper / torso` |

颈段只做**俯仰补偿**（`headPivot.rotation.x -= totalPitchX * 0.16`），扭转仍归
gaze 的 `headYaw`。两套来源各管一轴，不会互相抵消——这是刻意的：
扭头是「看哪里」，点头是「脊柱弯了要回正」，语义不同。

### 12.2 平衡量化：手臂配重是无效解，骨盆侧移才是

按第九节第 4 条的原计划，先做了「超界就加大另一侧手臂外展」的闭式解。实测：

> 手臂外展 40°，质心横移 ≈ 2mm（5kg / 70kg × 0.42m）。

这个量级对「重心出界」毫无帮助，直接删掉了实现的 `counterWeightAngle()`。
换成**骨盆平移**：上半身约占体重 60%，骨盆横移 1cm 就是实打实的 6mm 质心位移，
一个数量级以上的差距。

判定用捕获点而不是质心：`XCoM = COM + v·√(h/g)·τ·4`（τ 是反应时间常数）。
站立时速度项为 0，退化成 COM；走动 / 被击退时会把「正在往哪边倒」算进去。
投影到**双脚**包围盒（不是只算着地脚）——单脚支撑期只算着地脚的话，
余量会在 −1 与 +1 之间乱跳，读数没法用。

读数量纲：`score = 1 − max(|dx|/halfX, |dz|/halfZ)`，0 = 压线、1 = 正中。
待机实测剑盾 0.78、双剑 0.76、大剑 0.26——大剑偏低是**对的**：剑身伸出支撑面外，
真人拿大剑待机也确实要靠肌肉代偿。这类「分数低但有解释」比「永远 0.9」有用。

### 12.3 卡肉分层：让时长自己带出层次

分档不是新加一条通道，而是给现有 `hitstop` 表乘一个武器系数：

```
stop = table[受击类型] × hitstopByWeapon[武器]
     = { light 45ms, heavy 70ms, knock 100ms } × { 大剑 1.3, 法杖 1.1, 剑盾 1.0, 弓 0.9, 双剑 0.85 }
```

大剑 knock = 130ms、双剑 heavy = 59.5ms，差 2.2 倍，手感上就是「砍进去」和「划一下」。

表现层不另立档位表，而是**由时长反推**：`tier = clamp(dur / 0.1)`，
震动 = `0.34 + 0.48·tier`，微推 = `0.03 + 0.05·tier`（沿玩家→受击者方向）。
好处是 Core 调时长、表现自动跟上，不会出现「停得久却震得轻」的错位。

微推是位移式的（改 `camera.position`，不改朝向），衰减 `exp(-13t)`，
所以背景不旋转、只有一记「顶一下」的错位感。`diagnostics().camera.kick` 是包络值，
`kickCount` 是累计次数——后者用来确认「命中上升沿真的调到了」，不受采样时刻影响
（包络衰减快，采晚了就读成 0，这轮就被这个坑骗过一次）。

### 12.4 收势期间的下盘滑行

现象：攻击结束还在按方向键，收势（settle / recovery）那 0.2~0.3s 里角色在平移，
腿却停在攻击跨步姿态、脚被 IK 钉在原地，观感就是「滑过去」。

根因不是 IK，是**两条姿态来源打架**：攻击跨步姿态一直写到 `settle` 结束，
而移动步态在同一时间被按 0.3 的权重压着。修法是按**实际速度**做「移动接管」：

```
cap   = { windup 0.55, recovery 1.0, settle 1.0 }   // 各阶段最多让出多少
ramp  = clamp((speed - 0.35) / (1.2 - 0.35))        // 走起来了才接管
take  = cap × ramp                                  // 一阶平滑，上升 10 / 下降 6
gaitPose = mixLowerGait(gaitPose, realPose, take)
```

`mixLowerGait` 只插值**腿 + 骨盆**，保留攻击姿态的 `armL/armR/sideLean`——
上半身还在收招，下半身已经在走路，这才是「边收招边走」的真实分层。

A/B 对照判据换成两条更本质的指标（原来的「脚悬空高度」会被收势姿态本身抬腿干扰）：
**有没有一只脚落地**（`minLift < 0.08`）+ **单脚 z 行程 > 0.1**。
关掉接管时复现旧版：两只脚悬空 0.17m、行程 < 0.04m（等于站着被拖走）。

## 十三、v9s.34 落地记录：渲染插值、前馈补偿、工具提速

### 13.1 「慢放时动画更新小于渲染帧率」——是定步长，不是掉帧

现象描述很准，但根因不是性能：Core 固定 60Hz 步进（`fixedDt = 1/60`），
渲染按刷新率跑。`clock.frame()` 每帧把 `frameSeconds × timeScale` 累加进累加器，
够一个 `fixedDt` 才走一步。于是：

| 场景 | 模拟频率 | 渲染频率 | 观感 |
|---|---|---|---|
| 120Hz 屏幕、1.0× | 60Hz | 120Hz | 每两帧一张画，动作「卡在 60」 |
| 60Hz、0.25× 慢放 | **15Hz** | 60Hz | 每 4 帧才动一次，像幻灯片 |
| 60Hz、0.05× 慢放 | 3Hz | 60Hz | 几乎静止，偶尔跳一下 |

也就是说：**慢放不是把时间拉长，而是把采样率降低**。这对「看动作」是致命的。

修法是定步长渲染插值（`src/adapters/pose-interp.ts`）：

```
每步结束：posePrev ← poseCur；poseCur ← capturePose(world)
每帧渲染：alpha = 累加器剩余 / fixedDt
          world_for_render = applyPose(world, blendPose(posePrev, poseCur, alpha))
```

只插值**连续量**（位置 / 四元数级的朝向角 / 步相 / 攻击进度 / 受击计时），
离散量（武器、阶段、连击段、攻击 id、卡肉开始 / 结束）一变就整体 snap ——
否则跨段瞬间会被抹成两段之间的怪姿势。

两个必须注意的点：

- **角度要走最短弧**：`bodyYaw` 与 `gaitPhase` 都跨 ±π / 2π，线性插值会倒转一整圈；
- **代价是半帧延迟**（约 8ms）：这是 Gaffer《Fix Your Timestep》的标准取舍，
  换来任意刷新率下都连续。真机上如果觉得「跟手变钝」，先关 `view.renderInterp` 做 A/B。

用例把「抖动」量成了数字：0.25× 慢放下 60 帧，不插值时 35+ 帧是重复画面，
插值后 <3 帧；120Hz 下同样从 30+ 降到 <3，且**总位移不变**
（差值不超过一个模拟步的位移，说明没造假动作）。

### 13.2 平衡反馈：从「更用力」改成「更早」

v9s.33 的自动修正是纯闭环，`counterRate = 8`（τ ≈ 125ms）按「不抖」调的，
于是快速横移 / 被击退时修正永远慢半拍。这轮加了两条纯函数：

```
lateralFf = lateral + lateralSpeed × predLead        // predLead = 0.12s
rate      = counterRate × (1 + counterBoost × load)   // counterBoost = 1.6，load 夹到 2
```

两个刻意的边界：

- **外推会穿过中心时直接归零**（不是反号）—— 否则骨盆会在中心两侧来回抽；
- **双脚离地时前馈归零** —— 那时支撑面退化（`xcom` / `center` 都是 0），外推没有意义。

`predLead = 0` + `counterBoost = 0` 精确回到 v9s.33 行为，A/B 开关在配置里。

### 13.3 脊柱分段的一致性守卫

`splitSpine()` 是帧尾改写：之后 `upper.rotation` 只剩腰段（42% 在 `chest`）。
v9s.33 因此静默错了 5 处。这轮把它变成**可检测**：

- 新增 `torsoTotal()`（腰 + 胸），所有需要总角的代码走它；
- `splitSpine()` 记下拆分前的总角，帧尾比对残差写进 `spineDebug().leak`，
  用例断言恒为 0。谁在拆分之后再写 `upper` 当总角用，立刻能看到非零。

### 13.4 工具提速之后才看得见的两件事

clip-lab 九段全量从 **4m30s 降到 8.2s**（详见 `tools/clip-lab/README.md` 的耗时表），
于是「每次改完都跑一遍」终于成立。顺手纠正了一个诊断口径：

- **刃身衔接跳变天然一百多度**：段首按 `strike` 曲线淡入（`t=0` 时 ≈0），
  剑回到接近中位，段末是满幅。这不是数据错误，是淡入的位移量。
- **身体跳变才是「接上了没有」**：上段末 `bodyYaw` vs 下段起 `bodyYaw`，
  实测大剑 10° / 0°、剑盾 0°、双持 0° —— 躯干连续，三连击结构没问题。

顺带确认了一条**不是问题**的现象：大剑第三段工具读到仰角 +41.5°，
而配置里写的是 92.8° —— 因为 `bladePitch` 是挂点语义（剑身相对手臂），
工具在 `t=0` 读到的是「按 strike 淡入后」的姿态。想读设计值要把 strike 拉到 1。

## 十四、v9s.35 落地记录：朝向平滑，以及「插值清单」该怎么定

### 14.1 位置顺了，朝向为什么还顿

v9s.34 的插值让**位置**连续，但朝向暴露的是**角速度**：

- 0.25× 时模拟 15Hz，插值把「一步转 6°」摊成 4 段线性小坡；
- 速度在每段边界突跳一次 —— 位置是一阶量，看不出来；
- 手 / 肩 / 武器挂在 **0.4~0.8m 半径**上，角速度突跳 × 半径 = 线速度突跳，肉眼读作顿挫。

结论：**位置和朝向需要不同的平滑判据**。位置看「有没有卡住」，朝向看「速度有没有台阶」。

### 14.2 两层：根因层补数据，手感层加低通

| 层 | 做什么 | 为什么 |
|---|---|---|
| 根因 | 快照补齐 `velocity` / `dash.timer` / `turnInPlace.progress` / `playerLink.progress` / 假人速度 | 这些量表现层真的在读，15Hz 一跳就是姿态跳 |
| 根因 | 三套状态机的**阶段**进 `discreteKey` | 切阶段要 snap（翻滚起手 / 转身起步 / 举盾），阶段内部才连续 |
| 手感 | `renderInterp.yawSmoothMs`（35ms）低通渲染根节点 yaw | 抹平残余速度台阶；代价约半帧相位，不回写 Core |

低通的三条硬规则，缺一条就会出怪事：

1. **不回写 Core** —— 判定 / 命中 / 相机目标仍读 `bodyYaw`，否则「看着还没转过去就打到人」。
2. **瞬移必须穿过滤波器**（单帧 ≥ 60° 直接对齐）—— 否则传送 / 复位 / 换体型会横着飘过去。
3. **`0` 必须是精确的旧行为** —— A/B 只能改配置，不能改代码。

### 14.3 判据：不要用「平均平滑度」验收

`mean |Δyaw|` 几乎不变（抖和不抖转的总角度一样），`jerk` 在**等间隔帧**下插值已经压到
1e-4 量级，再加低通也不会更低（甚至略升）。真正该断言的是三件事：

- **画面不动帧数**（插值前后 180/240 → 0/240）—— 用户说的「一顿一顿」就是它；
- **单帧最大转角**（4.6° → 1.15°，0.25× 下 1.5° 是肉眼阈值附近）；
- **终点朝向**（三种显示方式差 < 0.1°）—— 证明平滑只改「怎么到」，不改「到哪」。

### 14.4 新增表现层字段时的规矩

1. 问一句「慢放到 0.25× 时它还会按 15Hz 跳吗？」—— 会跳就进快照（连续量）或进 `discreteKey`（离散量）。
2. 连续量一律在 `blendPose` 里走 `lerp`；角度 / 相位走 `lerpAngle`（最短弧）。
3. 在 `pose-interp.ts` 注释里写清「表现层哪里读它、不插值会怎样」——
   下一轮改表现层的人不必再猜这一层在管什么。

## 十五、v9s.36：命中时机必须落在「接触帧」上

### 15.1 现象与误判

「武器还没打到人就卡肉」听起来像表现层问题（平滑 / 滞后），实际是**判定时机**问题：

- 卡肉冻结的是 Core 的攻击时间轴（`phaseTimer` / 前冲 / 连击窗口），还在插值离散键里；
- 表现层「晚半帧再卡」= 逻辑停了画面还在走，解冻后要补跳，比不改更糟。

所以先问一句：**命中那一帧，`swingCurve(attackProgress)` 是多少？**
如果 < 0（蓄势），那就是「刀在身后就判了」——战场在 Core，不在渲染。

### 15.2 判据：命中帧的刃身角 vs 目标方位角

不要用「看起来像」验收，用两个数：

1. **命中时的 `attackProgress`**（或 active 内 `u`）；
2. **刃尖相对角 `ang(u)` 与目标方位角之差**。

剑盾第一段修复前后：`progress 0.217 / ang +160° / 刃尖离目标 2.0m` → `progress 0.362 / ang −2° / 0.33m`。

### 15.3 曲线从哪来：不要手写

用 `clipLab.preview({weapon, comboIndex, progress})` 把进度逐 5% 摆一遍，
读 `bladeWorld()` 的刃尖世界坐标，减去角色位置后反算 `atan2(x, z)`，
再减去 `attackFacing` 得到相对角。这条曲线**就是玩家看到的那把刀**，
而不是「按挥击手感估一个」。

改完剪辑（换关键帧 / 调节奏）必须重采一遍，否则判定会和画面重新错开。

### 15.4 三种段的写法

| 段型 | 写法 | 例 |
|---|---|---|
| 横扫（角度单调扫过） | `pts: [[u, ang], ...]`，命中要求目标角落在 `[ang(0), ang(u)]` | 剑盾 1/2 段、大剑 1/2 段、双剑 1/2/3 段 |
| 突刺（角度几乎不变） | `stabU`：`u >= stabU` 才判 | 剑盾第 3 段 |
| 下劈（角度变化大但慢） | 仍用 `pts`，它的角度区间最终会覆盖正前方 | 大剑第 3 段 |

### 15.5 规矩

1. **只推迟，不否决**：`reach` / `arcDeg` 不动，扫掠门只决定「什么时候开始算」。
   否则会变成「判定范围变了」，那是平衡改动，不是手感修复。
2. **每段独立可回滚**：某一段的曲线不对，删掉它的 `byCombo` 项即可回到旧行为。
3. **代价要写出来**：命中会晚 40~70ms（原本是提前判）。这不是新增延迟，
   是把「判定在刀前面」改成「判定跟着刀」，但对「按键→反馈」的体感是变慢的，
   所以 `tolDeg` 要留可调余量。

## 十六、v9s.37：卡肉是「节奏」，不是「暂停」

### 16.1 一个反直觉的事实

硬冻结（速率 0）看起来最「有力」，但它把**整段动作变长**了：45~130ms 的停顿全部加在这一刀上。
单发看不出来，三连就很明显 —— 越打越黏。战神的解法不是「冻结」，而是：

1. 命中瞬间把双方 **pop 到第一帧接触姿势**（不是随便冻一帧）；
2. **每一击都卡**，所以单次必须短（3~8 帧）；
3. 重量交给别的通道：重低频音效、大幅挥击弧线、夸张受击 —— 镜头震动反而**调小**。

### 16.2 三段式：保持 → 释放 → 偿还

| 段 | 速率 | 作用 |
|---|---|---|
| 保持 | 5% | 黏住。**不要设 0** —— 0 读作「游戏卡了」，5% 读作「砍进骨头里」 |
| 释放 | 5%→100% ease-out | 「脱开」的那一下。线性回 1 会显得软 |
| 偿还 | 150% | 把 hold+release 欠下的时间补回去，**总时长守恒** |

偿还必须封顶：`recovery × (payback-1) × 0.6`。不封顶的话，配置一改长就会在收招阶段
以 1.5× 抽搐式加速。

### 16.3 判据：看总帧数，不看单帧

「有没有变得更拖沓」唯一可靠的判据是**从起手到 idle 的总帧数**：

```
完全不卡 38   硬冻结 41   瓦片+偿还 38
```

同时要断言「保持期没有零速率帧」和「保持期进度仍在推进」—— 前者防止退回硬冻结，
后者防止把 holdRate 写成 0。

### 16.4 击地这类「圆形判定」的时刻怎么定

不要按「看起来像落地」猜。用 `npm run sweep -- --heights` 打印刃尖高度曲线，
取**穿过 y=0 的那一点**（大剑第三击是 u≈0.605，取 0.6）。
判定半径要和尘环半径是同一个数 —— 玩家应该能「看着圈躲」。

### 16.5 采样工具的三个坑

1. 刃尖是世界坐标，**必须减掉根节点实际 yaw**（`yawDebug().shown`）。角色在主循环里
   一直被索敌转过去，不减就会得到一条「随采样时刻漂移」的曲线。
2. 每个采样点要预热 ≥16 帧：腕部滞后 / 副手握持是有惯性的，跳进度后直接读是过渡帧。
3. `hitSweep.pts` 的 u 是 **active 内进度**，不是 `attackProgress`；
   换算 `(windup + u×active)/total`，搞错会整段偏移。

### 16.6 一个会骗人的坑：`clipLab` 会锁住主循环

`clipLab.preview()` 会把 `clipHold = true`，此时**主循环不再调 `view.render`**，画面停在上一次
preview 的最后一帧。于是「新加的贴地特效不显示」很容易被误判成特效代码有 bug —— 其实只是
主循环被锁住了。验证一次性特效（尘环 / 震动 / 刀光）必须先 `clipLab.release()`。

另外两条：

- 贴地环如果和角色脚下的「八向指示环」同半径、同色系，会完全看不出来。
  尘环要**更厚（≥18% 半径宽）、加色混合、颜色和 UI 明确区分**（现在用米白 #e8d8b0）。
- 环的半径就用**判定半径**，不要另配一个"看起来差不多"的数 —— 玩家会拿它当距离参考。
