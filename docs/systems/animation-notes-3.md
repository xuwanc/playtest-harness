> 最后更新：2026-11-09。**补充记录，不是规范**；规范见 [`animation.md`](animation.md)。
> 覆盖：命中必须落在接触帧（刃身扫掠门）、卡肉是节奏不是暂停（接触瓦片 + 偿还）、

## 十五、v9s.36：命中时机必须落在「接触帧」上

### 15.1 现象与误判

「武器还没打到人就卡肉」听起来像表现层问题（平滑 / 滞后），实际是**判定时机**问题：

- 卡肉冻结的是 Core 的攻击时间轴（`phaseTimer` / 前冲 / 连击窗口），还在插值离散键里；
- 表现层「晚半帧再卡」= 逻辑停了画面还在走，解冻后要补跳，比不改更糟。

所以先问一句：**命中那一帧，`swingCurve(attackProgress)` 是多少？**
如果 < 0（蓄势），那就是「刀在身后就判了」——战场在 Core，不在渲染。

### 15.2 判据：命中帧的刃身角 vs 目标方位角

不要用「看起来像」验收，用两个数：

1. **命中时的 `attackProgress`**（或 active 内 `u`）；
2. **刃尖相对角 `ang(u)` 与目标方位角之差**。

剑盾第一段修复前后：`progress 0.217 / ang +160° / 刃尖离目标 2.0m` → `progress 0.362 / ang −2° / 0.33m`。

### 15.3 曲线从哪来：不要手写

用 `clipLab.preview({weapon, comboIndex, progress})` 把进度逐 5% 摆一遍，
读 `bladeWorld()` 的刃尖世界坐标，减去角色位置后反算 `atan2(x, z)`，
再减去 `attackFacing` 得到相对角。这条曲线**就是玩家看到的那把刀**，
而不是「按挥击手感估一个」。

改完剪辑（换关键帧 / 调节奏）必须重采一遍，否则判定会和画面重新错开。

### 15.4 三种段的写法

| 段型 | 写法 | 例 |
|---|---|---|
| 横扫（角度单调扫过） | `pts: [[u, ang], ...]`，命中要求目标角落在 `[ang(0), ang(u)]` | 剑盾 1/2 段、大剑 1/2 段、双剑 1/2/3 段 |
| 突刺（角度几乎不变） | `stabU`：`u >= stabU` 才判 | 剑盾第 3 段 |
| 下劈（角度变化大但慢） | 仍用 `pts`，它的角度区间最终会覆盖正前方 | 大剑第 3 段 |

### 15.5 规矩

1. **只推迟，不否决**：`reach` / `arcDeg` 不动，扫掠门只决定「什么时候开始算」。
   否则会变成「判定范围变了」，那是平衡改动，不是手感修复。
2. **每段独立可回滚**：某一段的曲线不对，删掉它的 `byCombo` 项即可回到旧行为。
3. **代价要写出来**：命中会晚 40~70ms（原本是提前判）。这不是新增延迟，
   是把「判定在刀前面」改成「判定跟着刀」，但对「按键→反馈」的体感是变慢的，
   所以 `tolDeg` 要留可调余量。

## 十六、v9s.37：卡肉是「节奏」，不是「暂停」

### 16.1 一个反直觉的事实

硬冻结（速率 0）看起来最「有力」，但它把**整段动作变长**了：45~130ms 的停顿全部加在这一刀上。
单发看不出来，三连就很明显 —— 越打越黏。战神的解法不是「冻结」，而是：

1. 命中瞬间把双方 **pop 到第一帧接触姿势**（不是随便冻一帧）；
2. **每一击都卡**，所以单次必须短（3~8 帧）；
3. 重量交给别的通道：重低频音效、大幅挥击弧线、夸张受击 —— 镜头震动反而**调小**。

### 16.2 三段式：保持 → 释放 → 偿还

| 段 | 速率 | 作用 |
|---|---|---|
| 保持 | 5% | 黏住。**不要设 0** —— 0 读作「游戏卡了」，5% 读作「砍进骨头里」 |
| 释放 | 5%→100% ease-out | 「脱开」的那一下。线性回 1 会显得软 |
| 偿还 | 150% | 把 hold+release 欠下的时间补回去，**总时长守恒** |

偿还必须封顶：`recovery × (payback-1) × 0.6`。不封顶的话，配置一改长就会在收招阶段
以 1.5× 抽搐式加速。

### 16.3 判据：看总帧数，不看单帧

「有没有变得更拖沓」唯一可靠的判据是**从起手到 idle 的总帧数**：

```
完全不卡 38   硬冻结 41   瓦片+偿还 38
```

同时要断言「保持期没有零速率帧」和「保持期进度仍在推进」—— 前者防止退回硬冻结，
后者防止把 holdRate 写成 0。

### 16.4 击地这类「圆形判定」的时刻怎么定

不要按「看起来像落地」猜。用 `npm run sweep -- --heights` 打印刃尖高度曲线，
取**穿过 y=0 的那一点**（大剑第三击是 u≈0.605，取 0.6）。
判定半径要和尘环半径是同一个数 —— 玩家应该能「看着圈躲」。

### 16.5 采样工具的三个坑

1. 刃尖是世界坐标，**必须减掉根节点实际 yaw**（`yawDebug().shown`）。角色在主循环里
   一直被索敌转过去，不减就会得到一条「随采样时刻漂移」的曲线。
2. 每个采样点要预热 ≥16 帧：腕部滞后 / 副手握持是有惯性的，跳进度后直接读是过渡帧。
3. `hitSweep.pts` 的 u 是 **active 内进度**，不是 `attackProgress`；
   换算 `(windup + u×active)/total`，搞错会整段偏移。

### 16.6 一个会骗人的坑：`clipLab` 会锁住主循环

`clipLab.preview()` 会把 `clipHold = true`，此时**主循环不再调 `view.render`**，画面停在上一次
preview 的最后一帧。于是「新加的贴地特效不显示」很容易被误判成特效代码有 bug —— 其实只是
主循环被锁住了。验证一次性特效（尘环 / 震动 / 刀光）必须先 `clipLab.release()`。

另外两条：

- 贴地环如果和角色脚下的「八向指示环」同半径、同色系，会完全看不出来。
  尘环要**更厚（≥18% 半径宽）、加色混合、颜色和 UI 明确区分**（现在用米白 #e8d8b0）。
- 环的半径就用**判定半径**，不要另配一个"看起来差不多"的数 —— 玩家会拿它当距离参考。

## 十七、v9s.42：把相位画出来（sin 曲线 + 踩地分色）

`attackGaitDrive` 的相位是**看不见的**，调参时只能凭腿的观感猜。手感面板（`V` 键 /
顶部「手感」胶囊）第三区把它画成 `sin φ`：一个周期 = 一整步，横轴与上面两条曲线共用
同一个 6 秒窗口，所以「相位走到哪」和「速度掉到哪」能直接对齐着看。

| 相位 | 腿的状态 | 曲线颜色 |
|---|---|---|
| `sin φ > 0.16` | 左腿支撑相（踩地）/ 右腿抬起 | 琥珀 `#fbbf24` |
| `sin φ < −0.16` | 右腿踩地 | 紫 `#a78bfa` |
| `\|sin φ\| ≤ 0.16` | 换脚瞬间，双脚都在低位 | 灰 |
| 相位不推进（站定） | 双脚踩地 | 灰 |
| 双脚离地（跳跃 / 击退腾空） | 腾空 | 青 |

映射来自 `solveGait`：左腿取 φ、右腿取 φ+π，抬脚权重 `lift = (1 − sin φ) / 2`，
所以 `sin φ > 0` 就是左脚低、右脚高。

**三条实现上的坑**（都踩过）：

1. **不能读 Core 的 `gaitPhase`**。攻击时 Core 把移速锁成 0，`gaitPhase` 按实际位移推进，
   于是整段攻击它几乎是冻住的 —— 面板上会是一条平线，而腿明明在迈步。要读
   `voxel-rig` 暴露的「本帧真正喂给 `solveGait` 的相位」（`gaitDebug().phase`，
   攻击段由等效跨步驱动给）。
2. **不能拿速度判「在不在走」**。同样的原因：攻击时 `velocity` 与位移速度都是 0。
   唯一可靠的判据是**相位自己有没有推进**（一帧 > 0.02 rad）。推进 → 按 `sin` 判左右脚；
   不推进 → 双踩。
3. **低帧率下要插值补点**。软件渲染只有 ~10fps，6 秒窗口几十个点，直接连折线会把
   正弦画成锯齿；相位在帧间连续单调，按像素密度（每 ~2px）线性补点，曲线才是真形状，
   颜色切换点也随之更准。补点只影响观感，不改采样数据。

> 验收：`tests/v9s42-motion-phase.test.ts`（`stanceOf` / `wrapPhase` / 攻击段相位推进）、
> `npm run smoke`「手感面板：站着不动判双踩」「手感面板：走路时相位曲线左右脚交替」。

## 十八、v9s.43：换向为什么不能「一帧翻符号」

用户原话：**「前向移动切后向移动时 腿会抽一下」**。

`solveGait` 本身是 C∞ 的（只有 sin/cos 与一条 C¹ 的 `plantOffset`），所以第一反应是
「数学没问题」。问题不在曲线，在**乘在曲线前面的那个符号**：

```
前后摆幅 footZ = dirF × wF × (stride × reachRatio) × off(φ)
dirF = localForward >= 0 ? +1 : −1        // ← 硬符号
```

速度穿过 0 时 `dirF` 一帧取反，等于把整条腿位**镜像**过去。`wF` 这时并不小（纯前后移动
`wF ≈ 1`），而摆幅是按**步幅**定的（`stride/4`，恒 ≈0.36m），与速度无关 —— 于是
反向那一帧（实测 0.43 m/s）脚等效瞬移 0.5m，读数上就是单帧腿角跳 1.2 rad。

三个数字先量出来再改（`tests/v9s43-reverse-blend.test.ts` 里保留了对照）：

| | 注视锁定（原地倒走） | 不锁朝向（边转身边滑） | 左右横移 |
|---|---|---|---|
| 旧 | 1.06 rad | 1.26 rad | 1.21 rad |
| 新 | 0.55 | 0.55 | 0.55 |
| 正常跨步单帧 | 0.53 | 0.53 | 0.53 |

也就是说：**换向那一帧现在不比正常走一步更激烈**，再压下去意义不大（自然动作成了主导项）。

做法（`gait.ts`）：

```ts
// 骨架层每帧推一次符号；state 是 −1..1 的**线性**值
dirF = slewDirSign(dirF, drive.localForward >= 0 ? 1 : -1, dt, gaitCfg.dirFlipSec);
// solveGait 里再映射成两端速度为 0 的系数
const dirF = dirDrive(input.dirF ?? (localForward >= 0 ? 1 : -1));
```

- `slewDirSign` 匀速走 `|Δ|=2/sec` 的步长（`−1 → +1` 正好 `dirFlipSec` 秒）。匀速是刻意的：
  峰値单帧变化最小；smoothstep 会让峰值变成 1.5 倍。
- `dirDrive` 是 `sign(x)·smoothstep(|x|)`：`|x| = 1` 时逐位等于旧的 ±1（稳态零差异），
  0 附近衰减更快 → 腿在换向中点真正并拢，不会「一半镜像」。
- 左右轴 `dirR` 同一条通道。顺带把抬膝的领先量从 `lead > 0 ? 0.2 : 0` 改成
  `0.1 × (1 + side·dirR)` —— 旧写法在 `dirR` 过 0 时会让两条腿的抬膝差一帧跳一格。

### 三个坑

1. **不要按速度淡出**。看着「反正换向时速度很低」就想 `amp *= speed`，会把慢走削成碎步
   （v9o 踩过：低速巡航被误判成停步，腿冻住、身体平移 = 滑行）。摆幅归步幅管，只有
   **符号翻转**才需要淡。
2. **stale 状态要用「最终 drive」而不是 realDrive 推进**。攻击期间 `drive` 是
   `attackGaitDrive` 的等效驱动（符号可能和真实速度不同），用 realDrive 推进会让收招
   淡出段的两套姿态互相打架。顺序必须是：`realDrive → attackGaitDrive → drive → 推符号`。
3. **停步收相期间也要传同一组符号**。`solveStopGait` 用的是冻结的 `stopFwd/stopRight`，
   正常情况下符号与它同向；若换向恰好发生在收相窗口里，`dirF` 还在半途，摆幅会跟着
   收相进度一起衰减 —— 这比「切回硬符号」更安全（切换才是一帧跳变）。

> 数据：同目录 `v9s43-before.csv` / `v9s43-after.csv`（`dirFlipSec = 0` vs `0.16`，同一段输入）。

## 十九、v9s.44：朝向切换时，下盘为什么自己拧了一下

用户原话：**「朝向切换时，下盘会整体晃下，好像和 movedir 的切换有关」**。

### 它不是「角度不连续」

先用探针把整条轨迹打出来（速度方向固定，0.5s 内把 `bodyYaw` 扫 180°）：
`hipYaw` 从 0 爬到 **+24°**，再翻到 **−32°**，最后回 0。单帧最大 13.5°（810°/s），
而正常跨步单帧只有 0.53 rad（30°）。

`hipYaw` 的输出那层指数平滑（`hipYawSmoothing = 12`）本来就是连续的，所以问题不在
平滑，而在**目标本身**：`backHipYawTarget` 有两个「族」，身体转动时 θ 连续扫过
90° → 132°，两族在同一 θ 上差 ~100°，目标只能跳族。

| θ（身体局部移动方向） | 侧移族 | 后退族 |
|---|---|---|
| 90° | +50° | −90° |
| 99° | +49° | −81° |
| 112° | +44° | −68° |
| 132° | +31° | −48° |
| 180° | 0° | 0° |

`backStrafeKeep` 的 `flip = k²` 只在 100°~132° 之间过渡，于是那 30° 里目标要横穿
~97°：θ = 99° 时 +49°，θ = 112° 已经 −24°（实测单帧 52.7°）。

### 修法：身体自己在转的时候，胯不自己拧

物理上说得通：胯是被上身带过去的，不可能比身体本身转得还快。实现两层，共用一个
「转身闸门」`turnSpinGate(turnRate)`（30°/s 起、100°/s 满）：

```ts
const hipRate   = gaitCfg.hipYawTrackRateDeg * DEG;      // 默认 200°/s
const spinGate  = hipRate > 0 ? turnSpinGate(turnRate) : 0;

// ① 换族：转身期间停在侧移族
backHipYawTarget(bodyFwdRatio, latRatio, strafeYaw, backKeep, spinGate);

// ② 节流：目标最大转速
slewHipTarget(lastHipYawTarget, rawTarget, hipRate, dt, spinGate);
//   free = 1 - spin：
//   free = 1（没转身）→ rate ≈ FREE_RATE，等价于不限速，与旧行为逐位一致
//   free → 0（纯转身）→ rate → 0，目标冻住
```

`hipYawTrackRateDeg = 0` 时两层一起关（`spinGate` 直接置 0），精确回到旧行为，便于 A/B。

| 0.5s 转 180° | 旧 | 新 |
|---|---|---|
| 单帧最大变化 | 13.5° | 0.1° |
| 整体摆幅 | 57° | 0.5° |
| 反向过冲 | −32° | −0.5° |

> 图：`shots/v9s44/01-hip-yaw-turn.png`；数据：同目录 `v9s44-before.csv` / `v9s44-after.csv`
> （`hipYawTrackRateDeg = 0` vs `200`，同一段输入）。

### 三个坑

1. **一刀切限速会把「换向」也拖慢**。世界速度本身换向时（摇杆前推 → 后拉、身体朝敌人
   不动），θ 会在一瞬间翻 180°，下盘必须全速拧过去：腿的摆动轴 = 下盘前后轴，下盘
   跟不上就等于用错轴迈步。给所有情况都套 200°/s 时，v9s43「换向不抽腿」实测从
   0.55 掉到 0.63 rad（超过「正常跨步」这条线）。所以限速必须按**身体角速度**门控，
   而不是无条件。
2. **只冻目标、不冻输出**。`hipYaw` 自己那层指数平滑必须留着：转身结束时闸门一松，
   目标会一步跳到位（`free = 1` 时 rate ≈ 3400°/s），靠这层平滑把它摊成 ~0.2s 的
   追赶；连平滑一起冻住就会看到「转完卡一下再瞬间到位」。
3. **闸门开关处不能有跳变**。纯后退（θ = 180°）时两族都是 0°，所以最常用的那条
   路径上开关是连续的；真正的跳变只发生在 100°~180° 的斜后方，由节流兜住。
   另外 `turnRate` 必须用**未平滑**的 `wrapAngle(bodyYaw - prevBodyYaw) / dt`，
   用平滑过的值会让闸门比身体反应还慢半拍。
